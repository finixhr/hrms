# Finix HR — ChunkLoadError & Tenant Portal Performance Fix

**Date:** 2026-10-12 · **Scope:** Runtime ChunkLoadError crash, random portal crashes, performance regression

---

## 1. What was reported

| # | Symptom |
|---|---------|
| 1 | `Runtime ChunkLoadError — Failed to load chunk /the bundled chunk file under .next/static/chunks/ from module [project]/src/hrm/views/overtime.tsx [app-client] (ecmascript, next/dynamic entry, async loader)` at `AppShell` |
| 2 | The tenant portal randomly crashes after visiting a few pages; a manual refresh brings it back |
| 3 | The tenant portal has become much slower than before |

## 2. Root causes (three, compounding)

### RC-1 — `allowedDevOrigins` advertised the WRONG PORT (code bug — FIXED)

`package.json` runs the dev server on **port 4055**:

```json
"dev": "next dev -H localhost -p 4055"
```

but `next.config.ts` built the dev-origin allowlist from
`process.env.PORT || "3000"`. The `-p 4055` CLI flag **does not set
`process.env.PORT`**, so every allowlisted origin (`localhost:3000`,
`127.0.0.1:3000`, `<LAN-IP>:3000`) carried the wrong port. Next 16 therefore
rejected the **Turbopack HMR websocket from every host — localhost included**.

With HMR blocked, the browser tab kept a **stale chunk manifest**. Turbopack
recompiles on every file change (and on any touch from a cloud-sync client):
old chunk URLs are invalidated, but the tab never learns the new mapping. The
next lazy `next/dynamic` navigation (e.g. Overtime) requests a chunk that no
longer exists → **404 → the exact reported ChunkLoadError** → the error
propagates and unmounts the whole SPA → "crash". A manual refresh re-fetches
the current manifest → everything works again. This matches all three
reported behaviours precisely.

**Fix:** `devPort()` in `next.config.ts` now resolves the real port
(`-p/--port` CLI flag → `PORT` env → the repo's `4055` → `3000`), and the
allowlist covers `localhost` / `127.0.0.1` / every local IPv4, bare and with
both the live and legacy port. HMR now connects, the tab stays in sync with
recompiles, and stale-manifest crashes disappear at the source.

### RC-2 — The project runs inside the Google Drive sync folder (environment — ACTION REQUIRED)

The crash stack trace shows the build directory at
`..\..\Google\FHR\.next\dev\static\chunks\…` — the project (including `.next`)
lives **inside the Google Drive synced folder**. The previous working copy was
at `C:\HRMS_CCTV\` (see COMPLETION-REPORT-2026-10-12.md §6).

Turbopack continuously writes **thousands of chunk files** under `.next/dev`.
The Drive sync client locks, timestamps, uploads and re-touches every one of
them, which:

- causes massive disk I/O contention → the dev server gets **progressively
  slower the longer it runs** (RC-3's main driver);
- generates spurious file-watch events → **random recompiles** with no code
  edits → stale chunks even for a user who changed nothing;
- occasionally holds a chunk file mid-sync → transient chunk read failures.

**Action required on your machine** (code cannot fix this — the folder must
move):

1. Stop the dev server, then move the project **out of the Google Drive
   folder** to a plain local path, e.g. `C:\HRMS_CCTV\` (the previous
   location) or `C:\dev\FHR`.
2. If you must keep the source in Drive for backup, at minimum exclude the
   build folders from sync — in Google Drive settings, or keep the project
   local and back up only a zipped copy.
3. **Delete the `.next` folder once after moving** (stale Turbopack cache
   from the old location), then `bun install` if needed and `bun run dev`.

### RC-3 — No self-healing for transient chunk failures (code — FIXED)

Any transient chunk failure (dev-server restart while a tab is open, a deploy
swap in production, a network blip) hard-crashed the whole portal until the
user manually refreshed. The app now recovers by itself.

## 3. Code changes

| File | Change |
|------|--------|
| `next.config.ts` | `devPort()` resolves the actual dev port; `devOrigins()` trusts localhost/127.0.0.1/every local IPv4 on the live + legacy port (bare and host:port). Fixes the blocked HMR websocket that caused stale chunk manifests. |
| `src/hrm/chunk-recovery.ts` **(new)** | `isChunkLoadError()` — matches chunk-failure messages across Turbopack/webpack and Chrome/Firefox/Safari. `healStaleChunk()` — a guarded one-shot `location.reload()` (max once per 15 s, loop-safe). `withChunkRetry()` — one silent retry of a failed dynamic import before healing. |
| `src/hrm/views/registry.tsx` | All 42 lazy views now load through `lazyView()` → `withChunkRetry()` — transient chunk 404s retry silently instead of crashing. |
| `src/hrm/view-error-boundary.tsx` **(new)** | `ViewErrorBoundary` — contains any view load/render failure: chunk errors trigger the guarded self-heal (shows a "restoring…" state); real errors show an inline card with Retry / Reload. The sidebar and header stay alive — one broken view can never unmount the workspace again. |
| `src/hrm/app-shell.tsx` | `<ActiveView />` is wrapped in `<ViewErrorBoundary>` inside the per-navigation keyed container. |
| `src/hrm/home.tsx` | Global capture-phase `error` + `unhandledrejection` listeners funnel chunk failures from non-React paths into the same guarded reload. |
