## 2. Database / schema changes (additive only — existing data preserved)

- `User.mustChangePassword BOOLEAN NOT NULL DEFAULT false` — first-login forced password rotation for provisioned/reset accounts (existing rows default to `false`: current behavior unchanged)
- **NEW** `SaaSOwnerRole` table — owner-console role definitions (key, name, description, permissions JSON, isSystem, active). The 5 built-in template roles seed lazily as `isSystem=true` rows on first console access; custom roles are creatable/editable/deletable. `SUPER_ADMIN` cannot be deactivated or deleted; system-role keys are immutable.

Run after deploying: `bunx prisma migrate deploy` (then restart the app so the Prisma client matches).

## 3. Root causes fixed (not symptom patches)

1. **Create Employee → "Employee not found"** — `applyPayoutSelection` looked the employee up through the NON-transaction Prisma client while `employees.createWithStructure` was still inside its uncommitted `$transaction`; the new row was invisible → 404 → rollback → every create failed. The vendor id is now passed from the request context (the employee row is never needed for the settings read).
2. **Employee Directory search loses focus after every character** — `DataTable`'s `if (loading) return <LoadingRows/>` early-return unmounted the whole card INCLUDING the search input on every search-driven reload; the remounted input came back unfocused (and its fresh empty state re-fired a spurious `onSearch("")` echo). The toolbar/search box now never unmount — only the table body swaps loading/empty/error states — plus a first-render guard stops the mount echo.
3. **Delete button opened the profile** — `RowIconButton`'s click bubbled to the clickable `<tr>` (row navigation) while the delete dialog opened. Row buttons now stop propagation; the standalone Delete button was replaced by the permission-gated three-dot menu.
4. **Banks edit prefill would have written masked values** — `employees.get` returns masked account numbers (`•••• 1234`); the new edit dialog clears those fields and a blank submit keeps the stored value (matching the section-update handler's skip-empty convention).
