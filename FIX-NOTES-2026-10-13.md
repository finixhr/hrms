## 1. Payroll calculate crash — INT4 overflow (FIXED)

**Error**

```
prisma:error Invalid `prisma.payrollRun.update()` invocation:
ConnectorError ... ConversionError("Unable to fit integer value '5003650000'
into an INT4 (32-bit signed integer).")
[hrm] action=payroll.calculate ... at src\hrm-server\payroll.ts:471
```

**Root cause**

The H-09 paisa dual-write stores every money total as an integer paisa shadow
(`totalGrossPaisa = ROUND(totalGross × 100)`). Those columns were PostgreSQL
`INTEGER` (INT4), whose ceiling is **2,147,483,647** — about **Tk 2.14 crore
(21.47M)** in paisa. Your run's `totalGrossPaisa` was **5,003,650,000**
(≈ Tk 50M payroll), so the final `payrollRun.update` inside the calculate
transaction failed and the whole recalculation rolled back.

**Fix**

- **Schema**: all 27 paisa shadow columns widened `Int? → BigInt?`
  (PostgreSQL `INTEGER → BIGINT`) — `SalaryStructure` (10), `PayrollRun` (6,
  the ones that crashed) and `PayrollEntry` (11, same ceiling, per-employee
  totals). Migration: `prisma/migrations/9_wave6_paisa_bigint_20261013`
  (pure widening — no data changes, existing values preserved).
- **Writers**: `money.ts` `paisaOf()`/`structurePaisa()` and the payroll
  engine's `P()` now emit JS `bigint`, which is what Prisma requires for
  BIGINT columns.
- **API boundary**: the RPC dispatcher (`/api/hrm`) now JSON-encodes `bigint`
  as `Number` — Prisma BIGINT reads would otherwise crash
  `JSON.stringify ("Do not know how to serialize a BigInt")`. All app paisa
  values are far below 2^53, so the conversion is lossless. Handlers that
  return raw rows (payroll runs/entries, salary structures) keep working
  unchanged.
- **Tests**: h8/h09/m03 paisa suites updated for bigint reads/writes.

**Deployment action (required)**

```
bun run db:deploy        # applies 9_wave6_paisa_bigint_20261013
```

then re-run `payroll.calculate` on the failed run — the previously crashing
totals now persist.

## 2. Employee Action modal closes instantly + opens the profile (FIXED)

**Symptom**: Employee Directory → Employee Action (⋮) → e.g. "View Attendance
History" opens the modal, but clicking ANY control inside it (the date picker,
filter chips, inputs in Change Shift / Suspend dialogs) instantly closes the
modal and opens that employee's 360° profile.

**Root cause**

Every directory row is clickable (`onRowClick` opens the profile). The action
dialogs are rendered inside the row's React subtree. Radix portals their DOM to
`document.body`, but **React synthetic events still bubble through the React
tree**: a click on the date picker inside the portaled dialog bubbled up to the
`<tr onClick>` → `navigate(employees, { employeeId })` → the view switched,
unmounting the modal. (The three-dot menu itself was already patched with
`stopPropagation` — the dialogs were not.)

**Fix** — one guard in the shared `DataTable` (`src/hrm/shared/data-table.tsx`):

- row `onClick` now ignores clicks whose DOM target is **not inside the `<tr>`**
  (portal-mounted dialogs/dropdowns/selects/popovers never are), and
- row `onKeyDown` (Enter/Space) only fires when the row itself is focused.

This fixes the Attendance History modal, Change Shift, Suspend/Activate/Reset/
Create-Account confirms, Delete/Archive — and the same pattern in every other
clickable table in the app.

## 3. "Salary Processed" notification never marked as read (FIXED)

**Symptom**: the payslip notification ("Your salary for August 2026 has been
processed. Payslip PS-202608-0001 …") always stays unread; tapping it does
nothing.

**Root cause** — a scope mismatch between the three notification actions:

| action                    | old filter                                            |
| ------------------------- | ----------------------------------------------------- |
| `notifications.list`      | `userId = me` **OR** (`userId IS NULL AND employeeId = mine`) |
| `notifications.read`      | `userId = me` only                                    |
| `notifications.unreadCount` | `userId = me` only                                  |

Employee-addressed notifications (created with `employeeId`, no linked user at
creation time — exactly how the seeded payslip notification and several
automation paths create them) were **visible** in the list but could **never be
marked read** and never appeared in the badge count.

**Fix**: one shared `notifScope(ctx)` (same OR filter as `list`) now backs
`notifications.read` (single + "mark all read") and `notifications.unreadCount`,
plus the ESS dashboard's unread count (`ess.dashboard`). Anything a user can
see, they can now acknowledge — and nothing else (M-02 self-scoping intact).

## 4. Weekly off days — which of the three ways wins?

You asked whether all three assignment paths work and which overrides which.
Honest answer as found: **all three saved data, but the engines disagreed on
precedence** — the payroll engine resolved *shift → employee → global policy*
while leave, reports, the daily alert sweep and exit settlement resolved
*employee → global policy* and **ignored the shift entirely**. The same
employee could get different off days in different modules.

**Fix**: one canonical resolver — `resolveWeeklyOffDays()` in
`src/hrm-server/utils.ts` — now used by every consumer:

```
Employee profile (Edit Profile → Weekly Off Day(s))   ← most specific, WINS
  ↓ (empty → fall through)
Shift (Shifts & Roster → Weekly Off Day(s))
  ↓ (empty → fall through)
HR Settings → Workspace → General → Weekly Holiday     ← company default
```

Updated consumers: payroll engine (calculateRun), leave (day counting,
substitute eligibility, LEAVE-row writing), the daily attendance-alert sweep,
exit settlement OT rates, dashboard missing-attendance, and the OT ledger.
Empty values fall through, so an employee with no personal override follows
the shift; an employee on a shift with no off days follows the global policy.

Practical guide:

- Want a company-wide default? Set **HR Settings → Weekly Holiday**.
- Want it per shift/roster? Set the shift's **Weekly Off Day(s)** and clear
  the employee-level field for those employees.
- Want an exception for one person? Set **Edit Profile → Weekly Off Day(s)** —
  it beats both of the above everywhere.

## 5. Field Force → History → Employee: Location Hit Map (NEW)

**History tab** (new, between Locations and Reports): date range (default last
7 days) + employee filter. One row per **employee × date** — separate rows for
different dates — showing planned stops, completed, missed, ad-hoc visits, GPS
ping count and last activity, plus the **View Location Hit Map** button on
every row.

**Location Hit Map dialog** (`fieldforce.hitmap`):

- **dotted tracking line** of the day's GPS trail (TrackingPoint telemetry;
  downsampled to ≤600 drawn points with the stride disclosed);
- **duration of every stoppage**:
  - recorded visits — numbered pins colored by status, popup shows check-in →
    check-out and the stop duration, plus the server-computed distance and
    out-of-radius flag;
  - **derived stoppages** — amber "S" pins for stationary clusters in the GPS
    trail (≥3 minutes within ~75 m) that have NO recorded visit, each with its
    duration; clusters overlapping a recorded visit are not double-counted;
- planned-but-not-visited stops (slate pins + radius circles), ad-hoc visits,
  a summary strip (fixes, km travelled, planned/completed/missed/ad-hoc),
  a legend, and a chronological stoppage table under the map.

Server: `fieldforce.history` (per employee × date rows; one grouped SQL query
for ping counts in the deployment timezone) and `fieldforce.hitmap` (plan +
items + visits + trace + `detectTrackStoppages()`). Both are
`fieldforce.view`-gated and visibility-scoped (branch/dept managers see their
slice; cross-tenant ids → 404). `MapCanvas` gained a `fitTo` prop
(auto-fit bounds).

**Plan Editor — stoppage picker on the map (NEW)**: every stop row now has a
map button beside the location dropdown. It opens the existing map picker
(address search, click-to-place / draggable pin, radius slider + presets) and
the created location is **auto-selected for that stop** — so a stoppage
location with its area radius can be chosen directly on the map without
leaving the plan editor. "Add Stop" no longer requires locations to exist
first.

## 5. Unit-test database bootstrap (tests/preload.ts) — fixed

**Symptom:** `bun test tests/unit/ff-history-hitmap.test.ts` (any unit suite)
aborted in the preload with `P1000: Authentication failed … for 'postgres'`.

**Root cause (two layers):**

1. `bun test` runs with `NODE_ENV=test`, so Bun auto-loads **`.env.test`** — a
   committed template whose `TEST_DATABASE_URL` / `DATABASE_URL` carry the
   example credentials `postgres:postgres`. Those override the real values
   from `.env`, so the preload always ended up authenticating with the
   template password, which does not match a local server that uses any other
   password.
2. The old preload's last-resort fallback was the same
   `postgres:postgres@127.0.0.1:5432/hrm_test` URL — broken in exactly the
   same way, with no way to fall through to the working credentials.

**Fix — candidate probing in `tests/preload.ts`:** the preload now tries, in
order, (1) `TEST_DATABASE_URL` env var (or auto-loaded `.env.test`), (2)
`TEST_DATABASE_URL` in `.env`, (3) **derived from the `DATABASE_URL` inside
the `.env` FILE** — your real working credentials with the database name
swapped to `hrm_test` (the file is read directly precisely because `.env.test`
overrides the process env during `bun test`), (4) derived from the
`DATABASE_URL` env var, (5) the legacy default. The first candidate that
`prisma db push --force-reset` accepts wins — and `db push` **creates the
`hrm_test` database automatically** when it does not exist, so a fresh machine
needs no manual setup at all.

**Safety rails (new):** URLs containing "production" are still refused
outright, and any URL that points at the same server+database as a
development `DATABASE_URL` (from `.env` or the environment) is refused too —
`--force-reset` can never wipe a dev database. If nothing works, the preload
prints every attempted URL (password-masked) with the classified reason and
concrete fix instructions, then exits 1.

**Net effect:** with a working `DATABASE_URL` in `.env`, every unit suite now
runs with zero configuration: `bun test tests/unit/…` just works, and the
isolated `hrm_test` database is (re)created on each run.

## 6. Round-5 hardening — "fixes not visible on my server" (2026-10-13, late)

   If the tag is missing or older than the file on disk, the server is stale —
