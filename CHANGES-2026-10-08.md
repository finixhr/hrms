## 1. WP-A — Background Job System → full Job Queue Center

- **Schema (additive, migration 9):** BgJob += priority / scheduledFor /
  attempts / maxAttempts / cancelledAt / lastErrorAt / runLogJson +
  priority-aware claim index + per-type filter index. New statuses CANCELLED
  and DEAD (dead-letter) join PENDING/RUNNING/DONE/FAILED.
- **Engine (`jobs.ts`):** priority-aware claim scan (scheduledFor-aware),
  exponential backoff with jitter (2^attempts × 30s, cap 15 min, ±20%),
  automatic retry up to maxAttempts then DEAD, cooperative cancellation
  (CANCELLED checked between chunks via the progress callback; final writes
  conditional on status=RUNNING so CANCELLED always wins), per-type
  concurrency lanes, append-only run log (capped at 25 attempts).
- **Async conversions:** PAYROLL_CALCULATE / PAYROLL_PAY (progress hooks
  inside calculateRun/payRun every 25 employees — also cancellation
  checkpoints), ANNOUNCEMENT_DELIVERY (>200 audience), SALARY_EXPORT,
  ATTENDANCE_SWEEP (sweepOnce), DEVICE_SYNC (CHECK on all enabled devices),
  CAMERA_STATUS_SWEEP (WP-B). payroll.calculate/pay accept `async: true` →
  {jobId}; announcements.create fans out async for large audiences.
- **Job Center UI** (view `jobs`, perm jobs.view/jobs.manage — RBAC module
  added): 15s poll, status/type/date filters, detail drawer (full error, run
  log, redacted payload, result), Retry / Cancel / Requeue-from-DEAD actions,
  Scheduled tab (next run + cadence), failed-jobs badge.

## 9. WP-I — Online Payment Gateway

- Provider abstraction src/hrm-server/saas/payments/: types.ts
  (createSession / verifyCallback / handleIpn), SSLCommerz (sandbox + live),
  bKash checkout, Nagad — the documented API shapes; registry keyed by

- Flow: billing.pay.start creates the PENDING SaasPayment + hosted-checkout

  **public** /api/payments/return verifies SERVER-SIDE via the provider's
  validation API (redirect params never trusted) → settleGatewayPayment:

  Throttle rate-limited (30/10 min). Failure path: invoice stays PENDING,

  console REFUNDED). Currency BDT only.

## 10. WP-J — Automated Subscription Lifecycle

downgrades (from WP-H) are applied at cycle end by the same sweep.

### Errata (2026-10-08, post-release) — migration directory names

Prisma applies migrations in **alphabetical order of the directory names**.
The first packaging named the two new Wave-2 migrations `10_…` and `11_…`,
which alphabetically sort **between `1_…` and `2_…`**, so on any **fresh or
reset database** they ran before `5_saas_platform_20261003` (which creates
`SaaSPlan`) and failed with `P3018 / 42P01: relation "SaaSPlan" does not
exist`. Development was unaffected because migrations 9–11 were created on a
database that already had 0–8 applied. The fix renames the two directories
so they sort after `9_wave2_jobs_20261008` under every collation
(`9_wave2_jobs` < `9_wave2_modules` < `9_wave2_saas_ops` — decided at the
first differing letter, never at `_` vs digit):

- `10_wave2_modules_20261008` → `9_wave2_modules_20261008`
- `11_wave2_saas_ops_20261008` → `9_wave2_saas_ops_20261008`

Migration **contents are unchanged**; only the directory names moved.

- **Fresh installs / databases reset with the fixed names:** no action —
  `bun run db:deploy` (or `bunx prisma migrate reset --force`) now replays
  all 12 migrations in the correct order.
- **Databases that already applied the OLD names** (upgrades from the
  pre-Wave-2 release where `10_…`/`11_…` deployed successfully): after
  pulling the fixed names, mark the renamed migrations as applied:
  `bunx prisma migrate resolve --applied 9_wave2_modules_20261008` and
  `bunx prisma migrate resolve --applied 9_wave2_saas_ops_20261008`, then
  `bun run db:deploy`.
- **Broken fresh installs** (deploy failed with P3009/P3018 on `10_…`):
  rename the two folders as above and run `bunx prisma migrate reset
  --force`, or re-extract this fixed zip and reset.

**Future migrations must be named so they sort after `9_wave2_saas_ops…`
under any collation — do NOT use `10_`, `11_`, `12_` numeric prefixes
again.** Recommended: timestamp prefixes (Prisma's own convention, e.g.
`20261009093000_new_feature`) which sort chronologically and unambiguously.

Known cosmetic drift (pre-existing, harmless): the hand-written Wave-2 SQL
uses `TIMESTAMP` where `schema.prisma` implies `TIMESTAMP(3)`;
`migrate deploy` never checks parity, and a future `migrate dev` would
simply normalize this in the next migration.
